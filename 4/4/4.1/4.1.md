# 4.1. Módulo 1 / Integrante 1 (CHUPA)

### ADR-01: Validación atómica de disponibilidad mediante restricción de base de datos

- **Contexto:** Varias solicitudes de reserva pueden llegar casi al mismo tiempo sobre el mismo bloque de un profesional (CU-02; regla Citas #2 de [1.3](../1.3/1.3.md); escenario M1-R-01).
- **Decisión:** Usar una restricción de exclusión a nivel de base de datos (constraint de unicidad sobre profesional + bloque + estado activo) como mecanismo definitivo de consistencia, no solo una validación en la capa de aplicación.
- **Alternativas consideradas:** (a) bloqueo optimista solo en la capa de aplicación; (b) cola de reservas secuencial por profesional; (c) restricción a nivel de base de datos.
- **Justificación:** Un bloqueo solo en la aplicación no protege contra condiciones de carrera si el servicio de agenda corre en varias instancias en paralelo (necesario para la Escalabilidad de M1-E-01); la restricción de base de datos garantiza consistencia sin importar cuántas instancias del servicio existan.
- **Consecuencias / trade-offs:** Mayor acoplamiento al motor de base de datos relacional elegido; los conflictos de reserva deben comunicarse de forma clara al usuario para no perjudicar la Usabilidad (mitigado en ADR-05).
- **Componentes afectados:** Servicio de Agenda, esquema de base de datos de Citas.

### ADR-02: Índice compuesto (tenant, profesional, fecha) para consultas de agenda

- **Contexto:** La vista de agenda del día y la agenda mensual deben responder rápido incluso con alto volumen de citas (CU-09; escenarios M1-R-02 y M1-E-02).
- **Decisión:** Crear un índice compuesto sobre (tenant_id, profesional_id, fecha) en la tabla de bloques/citas.
- **Alternativas consideradas:** Confiar únicamente en el índice primario; cachear la disponibilidad en memoria en vez de indexar.
- **Justificación:** Sostiene el crecimiento de citas por establecimiento (de 50 a 500 diarias, M1-E-02) sin degradar el tiempo de respuesta, con una solución estándar de base de datos en vez de introducir una capa de caché adicional que mantener.
- **Consecuencias / trade-offs:** Costo adicional en cada escritura (insertar/actualizar una cita); aceptable porque las lecturas de agenda son mucho más frecuentes que las escrituras.
- **Componentes afectados:** Esquema de base de datos de Citas.

### ADR-03: Réplica con conmutación por error para el servicio de agenda

- **Contexto:** El núcleo de validación de disponibilidad es un punto único que, si falla, bloquea todo el ciclo de citas (escenario M1-D-01, objetivo: 99.5% de disponibilidad en horario de atención).
- **Decisión:** Desplegar una réplica de base de datos con conmutación (failover) automática para el servicio de agenda.
- **Alternativas consideradas:** Respaldo periódico sin failover automático (tiempo de recuperación alto, no cumple el objetivo de <30 s); arquitectura activo-activo multirregión (mayor costo y complejidad, no justificada para el tamaño de los establecimientos objetivo).
- **Justificación:** Cumple el objetivo de recuperación en menos de 30 segundos sin incurrir en la complejidad de una arquitectura multirregión, adecuada para establecimientos de 2 a 15 profesionales (contexto de [1.1](../1.1/1.1.md)).
- **Consecuencias / trade-offs:** La réplica es un componente de infraestructura adicional que operar y monitorear (impacto en Mantenibilidad); se acepta porque la Disponibilidad es más crítica en este módulo.
- **Componentes afectados:** Infraestructura de base de datos del Servicio de Agenda.

### ADR-04: Portal de autoservicio del paciente desacoplado de la admisión presencial

- **Contexto:** El paciente debe poder reservar una cita fuera del horario de atención presencial, incluso si el sistema de admisión interno está en mantenimiento (escenario M1-D-02).
- **Decisión:** Separar el frontend/API del portal de autoservicio del paciente del que usa Recepción para la admisión presencial, ambos consumiendo el mismo Servicio de Agenda central pero con despliegues independientes.
- **Alternativas consideradas:** Una sola aplicación monolítica compartida entre Recepción y el paciente.
- **Justificación:** Permite que el portal de autoservicio siga operativo aunque el módulo de admisión presencial esté degradado (o viceversa), reduciendo el radio de impacto de una falla puntual.
- **Consecuencias / trade-offs:** Duplica parcialmente el esfuerzo de mantenimiento de interfaz (dos frontends en vez de uno); se acepta por el beneficio de disponibilidad diferenciada entre canales.
- **Componentes afectados:** Portal de autoservicio del paciente, aplicación interna de Recepción.

### ADR-05: Validación en dos capas (frontend + backend) para la reserva de citas

- **Contexto:** La regla Citas #3 de 1.3 exige que el frontend impida enviar una reserva incompleta, pero que la validación final de disponibilidad y duplicidad corresponda siempre al núcleo del sistema (escenario M1-U-01).
- **Decisión:** El frontend bloquea el envío con campos obligatorios vacíos, pero el backend siempre revalida disponibilidad, duplicidad y aislamiento por tenant, sin confiar en lo ya validado por el cliente.
- **Alternativas consideradas:** Confiar solo en la validación del frontend (más simple de implementar, pero permite condiciones de carrera o manipulación del cliente).
- **Justificación:** Cumple explícitamente la regla Citas #3 y mejora la experiencia del paciente nuevo (M1-U-01) sin sacrificar la integridad garantizada por ADR-01.
- **Consecuencias / trade-offs:** Las mismas reglas de validación deben mantenerse en dos capas (frontend y backend), con el riesgo de que diverjan si no se centralizan bien.
- **Componentes afectados:** Portal de autoservicio del paciente, Servicio de Agenda.

### ADR-06: Aislamiento multi-tenant mediante filtro obligatorio de tenant en la capa de acceso a datos

- **Contexto:** Ningún dato de un establecimiento puede ser visible desde otro tenant (regla General #1 de 1.3; escenario M1-S-01, meta 0 incidentes de fuga entre tenants).
- **Decisión:** Centralizar el filtro por `tenant_id` en la capa de acceso a datos (no dejarlo a criterio de cada endpoint), de modo que toda consulta al padrón o a la agenda lo aplique automáticamente.
- **Alternativas consideradas:** Una base de datos completamente separada por tenant (aislamiento más fuerte, pero costo operativo alto para un modelo SaaS con muchos establecimientos pequeños); confiar en que cada desarrollador filtre correctamente en cada consulta (alto riesgo de error humano).
- **Justificación:** Balancea un aislamiento sólido con un costo operativo razonable para establecimientos pequeños (contexto de 1.1); centralizar el filtro reduce drásticamente el riesgo de una fuga por omisión en un endpoint nuevo.
- **Consecuencias / trade-offs:** La capa de acceso a datos se vuelve un componente crítico de seguridad que exige pruebas exhaustivas y revisión obligatoria en cada cambio.
- **Componentes afectados:** Capa de acceso a datos (repositorios) de Pacientes y Agenda.
